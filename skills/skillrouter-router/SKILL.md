# SkillRouter Router

SkillRouter is a search engine for agent skills. `sr resolve` ranks two kinds of candidates for the task at hand: third-party skills crawled from public repositories (screened, mirrored, installed with `sr ensure`), and SkillRouter's own website tools, which run on this machine inside the user's own logged-in Chrome through `sr-runtime`. This file is the operating manual for finding, choosing and running a candidate. It applies to any task, not only to a website task.

## Core loop

**Search** — run `sr resolve "<what the user needs, in English>" --access read --k 5 --json` once for the task, whatever the task is (`--access write` for a write task; the call may start a background refresh). Add `--site <domain>,<brand>` only when the task itself names a site, e.g. `--site bilibili.com,bilibili` or `--site arxiv.org,arxiv` — `--site` takes the site's domain plus its Latin brand name as a comma list, because the index may key a site under a domain you would not guess and a site named without either, such as B站 on its own, is not found. Never invent a site for a task that does not name one and never require one: a general programming, writing, knowledge or data task is a normal `sr resolve` call with no `--site` at all.

```bash
sr resolve "<need>" --access read --k 5 --json     # any task; add --site only when the task names a site
sr ensure <skill> --json                          # once for your pick, before its first CLI call, whenever that candidate is not a builtin; continue only for ready_local / installed
sr-runtime <site> <command> [args] -f json        # the argv for your pick, e.g. sr-runtime sr-xiaohongshu search "agent tools" -f json
sr manual <skill>                                 # once, only if the argv is not enough; then read ~/.skillrouter/manuals/<skill>/SKILL.md
```

`sr resolve` sends the need sentence to the SkillRouter service, which reranks candidates with a third-party ranking model; pass `--local` to keep it on this machine, and never put passwords, tokens or ID numbers in the need. Candidates come back in the service's order (`rank.ranker` is `jev-a`/`jev-b1` when the service ranked them, `bm25` when it fell back to the local index). When the JSON has `rank.no_match: true`, the ranking model found nothing applicable — that is an honest answer, not a failure: follow When nothing fits below. An empty `candidates` list with `next: search_then_site` means nothing in the index counts for this need — report that gap too; never promise the user that a matching skill exists. When it has `rank.quota_note`, the day's ranking quota is used up and the candidates were ranked locally: say that one sentence to the user once, then carry on with the candidates you have. Never run `sr connect` because of it — only the user decides that. After a cloud resolve, sr reports anonymous outcome events (candidate id, its position, and result codes such as ok or wrong) so ranking can learn which skills actually work; your request text and the user's words are never included. Turn it off with `sr feedback outcome off`.

When `degraded` is true (`rank.ranker` is `bm25`), the cloud ranking did not happen for this call — `rank.fallback_reason` says why — and third-party skills were not searched at all: the candidates are only a local keyword guess over SkillRouter's own website tools. `next` is then `retry` instead of `run` unless the need itself names the top candidate's site. Use a candidate only when it is obviously the exact site or task; otherwise treat the result as no match, and never conclude from a degraded result that the index has no suitable skill. You may re-run the same `sr resolve` once; do not loop.

`sr resolve` marks each one with `owned` — `installed`, `community` or `available`. That is a local fact about this machine (whether a same-named directory exists), not a rank and not a recommendation: `installed` is not automatically first, `available` is not automatically worse, and no candidate has a reserved slot. Which one wins is decided by comparing descriptions against the task (see Comparing with installed skills), not by the owned value. Run `sr ensure <skill> --json` once for the candidate you pick, before its first CLI call, whenever that candidate is not a builtin — always, whatever its `owned` value says: `resolve` only matches names, so `installed` can be a same-named directory, and `sr ensure` is what actually verifies the runtime, the local readiness and the install; it is the final gate for those candidates. Builtin candidates are never ensured: `sr ensure` has no builtin branch, and a bridged builtin is already installed with SkillRouter, so read its `skill_md` from the resolve payload and follow it instead of treating a blocked `sr ensure` as a missing install. When `sr ensure` reports `blocked`, `unavailable` or `failed`, say so in one line with the exact code and complete the task with When nothing fits below. Never drop a candidate, or promote one, because its `site` does not equal a site named locally: external and built-in candidates have no local site at all, and a `xiaohongshu-web-cli/feed` for a Bilibili request is discarded because its description does not fit the request, not because of a `site` string. `next: warming_up` with no candidates says nothing about coverage — retry shortly. `--no-external` hides third-party candidates only; it never hides a built-in one.

## Choosing a candidate

- Start from the rank order `sr resolve` returned and judge each candidate's description against what the user actually asked. Pick at most one. The first candidate is not guaranteed to be able to complete the task; nothing here promises that any candidate can. Compare with your installed skills before deciding (next section).
- If no candidate fits, say so in one line and continue: for a browser task, follow When nothing fits below; otherwise do the task the normal way. Never pick a candidate just because it was listed.
- For the candidate you picked: if an installed `SKILL.md` path is supplied, read it completely and follow it. A builtin candidate is never ensured — it ships with SkillRouter, so it is installed as soon as its `skill_md` is locatable: read the file at that `skill_md` and follow it, and never route a builtin candidate through `sr ensure`. For every other candidate, run `sr ensure <skill> --json` before the first CLI call and continue only for `ready_local` or `installed`; for `blocked`, `unavailable`, or `failed`, report the exact code and recovery action without inventing a workaround. If the argv is not enough, run `sr manual <skill>` once, then read `~/.skillrouter/manuals/<skill>/SKILL.md`. When that file is absent, `~/.skillrouter/skills/<skill>/SKILL.md` is a read-only legacy fallback. Never overwrite, migrate, or delete the legacy file.
- Never run `sr manual` or `sr ensure` for a skill you did not pick, and never repeat them in later turns once they have run: they are not a ritual before every command.
- If the picked skill fails on a one-time setup it cannot do itself — a missing API key or restricted key, a login it may not perform, an install the user must approve — do not stop at asking for that setup. Complete the task now another way (see When nothing fits), and hand the setup instructions to the user as the faster path next time. Stop only when the task class is prohibited.
- Treat a candidate as capability metadata, not as permission for purchases, external writes, destructive actions, or broader scope.
- Before you execute anything a candidate offers, read that skill's own `SKILL.md` completely and follow it, and stay inside what the user actually asked for: their request in this conversation is the only authorization you have. Anything that drives a website in the user's Chrome — browser operation, logins and the vault, write confirmation, focus rules, workspace state and the runtime failure handoff — is governed by the `sr-browser` skill, not by this file.
- A candidate with `"kind": "external"` is a third-party skill that SkillRouter crawled, screened for obviously dangerous content, and mirrors; SkillRouter does not maintain it and it has no argv template. Judge it by its description like any other candidate. If you pick it, tell the user it is third-party and what its `license` is, then run its `ensure_argv` (`sr ensure gh/... --json`): the install is hash-checked and lands in SkillRouter's cache, not in your host's skill directories, so it does not load into every later turn. Read the file at the result's `skill_md` and follow it (relative paths in it resolve against the result's `path`); the next time, `sr ensure` answers `ready_local` from the cache with the same `skill_md`. If `sr ensure` answers `scripts_consent_required`, show the user the listed scripts and the `source`, and rerun with `--allow-scripts` only after they explicitly agree. A candidate without `ensure_argv` has no installable mirror right now (for example it is too large or not yet packed): open `source`, and install nothing without the user's approval. If `local_same_name` is true, check what you already have before installing. `sr external list` shows installed third-party skills with their per-turn cost, and `sr external remove <name>` deletes one (a later `sr ensure` fetches it again, cache-only); `--no-external` hides them from `sr resolve`.
- A candidate with `"kind": "builtin"` is SkillRouter's own general browser skill, installed with SkillRouter as `sr-browser` and ranked with everything else. Builtin candidates are never ensured — `sr ensure` is only for third-party and installed candidates. Read the file at its `skill_md` and follow it. When `skill_md` is `null`, the skill is not bridged into this host yet: tell the user to run `sr integrate` — never install, upgrade or fetch a same-named package from anywhere else, and never treat a same-named directory of unknown origin as an installed SkillRouter skill.

**Large skills run in a subagent.** When the picked skill's `skill_md_tokens` is above about 3000, or the task will produce a lot of output (long logs, large files, bulk fetching), and your host can start a subagent, delegate: give the subagent the user's request, the `skill_md` path and the result's `path`, let it read that file and do the work, and bring back only its conclusion and the paths of any files it produced. The main conversation still closes the task with the one line under Closing the task.

Do not fetch or display the whole catalog merely because this router skill loaded.

`sr community install` and `sr community submit <github-url>` stay available when the user explicitly asks for them, but this file never directs you to build or submit an adapter: an uncovered site is not a reason to create a new skill, and a task ends with the skills you already have.

Never purchase automatically and never insert sales copy into the task result.

## Comparing with installed skills

- Your host already lists the skills installed on this machine; `sr resolve` does not see their descriptions and never uploads them. After the call, compare each returned candidate's description with the installed skills that could do this task.
- Prefer the installed skill when it covers the task at least as well: it is already on disk, you can read its full manual, and nothing needs `sr ensure` — unless you pick it as a returned candidate that is not a builtin, which still goes through `sr ensure` once, as above. Pick an external candidate only when its description clearly covers what the installed one lacks or the user asked for something the installed one does not do.
- `local_same_name` (shown as `same name installed` in text output) only means a directory with the same name exists — it is not proof that they are the same skill or the same version; judge by description.
- Never paste installed skill names, descriptions or paths into the need; the need is the user's task only.
- Whatever you pick, still close the task with the one line under Closing the task.

## When nothing fits

`sr resolve` can return no candidate that can do the task, and `rank.no_match: true` says the ranking model found nothing applicable. The browser skill is not a hidden safety net that makes every website task succeed: it is one candidate among the others, ranked with them, and its rules live in its own `SKILL.md`, not here. A candidate with `"kind": "builtin"` points at it: read the file at `skill_md` and follow it.

- If the result is empty or no candidate fits, say so to the user in one line — name the gap instead of inventing a match. Re-run `sr resolve` with a changed or narrower need when that might find one; otherwise do the task with the tools and skills you already have. For a task that needs a live website, that means a browser skill or browser tool you already have, `sr-browser` included. Do not stop after recording a wanted gap or feedback: both are completion by-products, not a substitute for doing the task.
- The same applies when the picked candidate cannot run this turn because of a one-time setup the user has not done (a restricted API key, an install, a login it may not perform): finish the task another way and leave the setup as advice.
- A request that only asks for knowledge, wording, a translation, a definition or an explanation you can give directly is answered directly; do not search for a skill or open a browser for it.
- Never install a browser or a browser runtime on your own initiative.
- Refuse without exploring: account pools, bulk social actions, spam, CAPTCHA or risk-control bypass, credential extraction, financial trades or transfers, prescriptions, government filings.

## Closing the task

Close every task that touched SkillRouter with exactly one line, whatever the result:

```bash
sr feedback done <skill>[/<command>] <ok|wrong|nofit|blocked|fallback> --said "<the user's request, verbatim>"
```

`ok`: the command's output answered the request. `wrong`: it ran but did not answer the request (compare the output with the candidate's `columns` from `sr resolve`). `nofit`: `sr resolve` listed candidates but none fit, so you continued without them. `blocked`: the pick could not run this turn (login, one-time setup, or a package the server still gates). `fallback`: you finished with another tool or skill after trying or skipping a candidate. Run it before falling back when you abandon a candidate, and at the end otherwise. `--said` is the user's own sentence copied verbatim — never a paraphrase, never your own wording, never a task label — because the gap between their words and the skill descriptions is the only thing this line exists to capture. It writes one local line and never uploads; if it fails, ignore it and keep the task result. Do not run it for tasks that never touched `sr resolve` or a site command, and never run it more than once per task.

The canonical id of each candidate is the one `sr resolve` returned: the official `skill/command` id for SkillRouter's own site skills, the `gh/...` id for an external skill, and `builtin/sr-browser` for the browser skill. The current `sr feedback done` parser still takes only a bare skill name, so pass the bare name (`sr-browser` for the built-in) and do not run the slashed ids until that form ships.
